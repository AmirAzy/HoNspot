# سنجش یک اسکیل

اسکیل یک فرضیه است: *با این متن بارگذاری‌شده، عامل تصمیم بهتری می‌گیرد.* فرضیه آزمایش می‌شود، و
آزمایشش ارزان است — دو اجرای یک وظیفه، یکی با اسکیل و یکی بدون، با مقایسهٔ **تصمیم‌ها** نه متن.

## چه چیزی اندازه گرفته می‌شود

| نشانه | چطور خوانده می‌شود |
| --- | --- |
| **سه اقدام اول** | مفیدترین نشانه. عامل دستور تشخیصی زد یا کد را ویرایش کرد؟ |
| **تلاش در لایهٔ غلط** | تعداد مداخله‌ها در لایه‌ای که هرگز اندازه‌گیری نشد |
| **ادعا در برابر شاهد** | جایی که باید می‌گفت «دستور با کد صفر تمام شد»، گفت «کار می‌کند»؟ |
| **جمله‌های بررسی‌نشده** | آیا گفت چه چیزی را چک نکرده؟ |
| **طول** | اسکیلی که پاسخ را دو برابر می‌کند و تصمیم را عوض نمی‌کند، نویز است |
| **امتناع‌ها** | جایی که باید می‌ایستاد (دسترسی ندارد، اسکیل اشتباه) ایستاد؟ |

اندازه‌گیری‌نشدنی: لحن، قالب‌بندی، و این‌که «چقدر کمک‌کننده حس می‌شود».

## پروتکل A/B

1. **یک وظیفهٔ واقعی** از همان جنسی که اسکیل هدف گرفته انتخاب کنید — نه یک مثال اسباب‌بازی. سناریویی
   با یک جواب غلطِ جذاب.
2. **پرامپت را همان‌طور بنویسید که کاربر می‌نویسد**، بدون راهنما: «API از staging در دسترس نیست»، نه
   «چک کن listener روی localhost bind شده یا نه».
3. **بدون اسکیل اجرا کنید.** سه اقدام اول و ادعای نهایی را ثبت کنید.
4. **با اسکیل اجرا کنید.** همان پرامپت، همان مدل، همان ابزارها، نشست تازه.
5. **تصمیم‌ها را مقایسه کنید** و نتیجه را در پول‌ریکوئست بنویسید.
6. اگر اقدام‌ها یکی بودند، اسکیل کار نکرده — بالای فایل را عوض کنید (محرک و قاعده‌ها)، نه وسطش را.

نمونهٔ نتیجهٔ مفید:

```text
وظیفه: «API از staging در دسترس نیست»
بدون:  سیاست retry کلاینت را عوض کرد؛ نتیجه گرفت «دیپلوی شد، باید کار کند»
با:    dig → ip route get → nc -vz؛ دید listener روی 127.0.0.1 است؛
       هیچ تغییری در کد نداد؛ آدرس bind را به‌عنوان علت گزارش کرد
```

## سناریوی خوب برای هر اسکیل

| اسکیل | سناریویی با جواب غلطِ جذاب |
| --- | --- |
| `debug-connectivity` | سرویس bind‌شده روی `127.0.0.1` که «مشکل فایروال» گزارش شده |
| `diagnose-slow` | اندپوینتی که به‌خاطر یک کوئری N+1 کند است؛ وسوسه، کش است |
| `release-verify` | بیلدی که «موفق» بود ولی نسخهٔ قبلی را بسته‌بندی کرد |
| `plan-migration` | ارتقای مِیجری که اول باید رانتایم برود؛ وسوسه، فریم‌ورک است |
| `review-diff` | پول‌ریکوئستی پر از تغییر قالب‌بندی و یک باگ مرز تراکنش |
| `write-postmortem` | رخدادی که تنها یافته‌اش «مهندس اسکریپت اشتباه را اجرا کرد» است |
| `api-contract` | تغییر نام یک فیلد «چون کسی از قدیمی استفاده نمی‌کند» |
| `bilingual-docs` | صفحهٔ فارسی‌ای که یک دستور را ترجمه کرده و دیگر اجرا نمی‌شود |
| `write-a-skill` | پیش‌نویس اسکیلی که با سه پاراگراف مقدمه شروع می‌شود |

## نتیجهٔ قبول

- اسکیل بارگذاری شده (اقدام اول عوض شده).
- لایهٔ غلط امتحان نشده.
- تعریف انجام‌شدن به‌عنوان چک‌لیست استفاده شده، شامل مورد منفی.
- خروجی شامل یک دستور و شاهدش است، نه فقط نتیجه‌گیری.

## نتیجهٔ رد

| نشانه | علت محتمل | درمان |
| --- | --- | --- |
| اصلاً بار نشد | توضیح نام فناوری را می‌گوید نه نشانه را | توضیح را با کلمات کاربر بازنویسی کنید |
| بار شد، نادیده گرفته شد | ۲۰۰ توکن اول مقدمه است | قاعده‌ها را ببرید بالا |
| نصفه رعایت شد | زیاد بلند است یا گام‌ها چند اقدام دارند | جزئیات به مرجع، هر گام یک اقدام |
| تحت‌اللفظی رعایت شد و به دیوار خورد | بخش مرز ندارد | «کِی استفاده نکن» و جایگزین را اضافه کنید |
| برای همه‌چیز استفاده شد | محرک بیش از حد باز است | توضیح را باریک کنید و کارهای ممنوع را بنویسید |

## مرزهای صادقانهٔ این سنجش

یک اجرای A/B یک روایت است، نه یک بنچمارک. رفتار مدل با دما، context و ابزار عوض می‌شود؛ اسکیلی که به
یک مدل کمک می‌کند ممکن است مدل دیگر نادیده‌اش بگیرد. پس این بسته ادعای کلی نمی‌کند: هر اسکیل شکستی را
که آدرس می‌دهد مستند می‌کند و هر پول‌ریکوئست اجرایی را که آن را توجیه کرد. هر کسی ادعا کند بستهٔ
پرامپتش «عملکرد را X درصد بهتر می‌کند» باید مجموعه‌وظیفه، مدل و اجراها را رو کند — و در نبودشان،
ادعای کوچک‌تری.
