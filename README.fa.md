# Hone

**یه مجموعه جمع‌وجور از اسکیل‌های کاربردی برای ایجنت‌های هوش مصنوعی که کدنویسی می‌کنن. ۹ اسکیل، بدون وابستگی، بدون اسکریپت نصب؛ فقط دستورالعمل‌هایی که کمک می‌کنن AI به‌جای حدس زدن، درست و حسابی کار کنه.**

[English](README.md) · **فارسی**

وقتی به یه AI دستورالعمل مشخص ندی، ممکنه با اعتمادبه‌نفس کامل اشتباه کنه!

مثلاً ازش می‌پرسی چرا دو تا سیستم به هم وصل نمی‌شن، به‌جای اینکه مشکل اتصال رو بررسی کنه، می‌ره یه کتابخونه جدید برای پیدا کردن دستگاه‌ها نصب می‌کنه.

می‌گی نسخه نهایی رو بیلد و منتشر کن، فقط چون یه فایل ساخته شده، اعلام می‌کنه همه‌چیز موفق بوده!

یا ازش می‌خوای کدت رو بررسی کنه، کلی ایراد ظاهری و جزئی پیدا می‌کنه ولی یه باگ جدی که باعث از دست رفتن اطلاعات می‌شه رو نمی‌بینه.

**Hone دقیقاً برای جلوگیری از همین اشتباه‌ها ساخته شده.**

هدفش این نیست که یه فریم‌ورک رو به AI آموزش بده؛ هدف اینه که قبل از هر ادعایی، اول بره شواهد رو بررسی کنه و مطمئن بشه واقعاً کاری که می‌گه انجام شده.

هر اسکیل یه پوشه جدا داره که داخلش فایل `SKILL.md` قرار گرفته. این فایل مشخص می‌کنه اسکیل چه زمانی باید فعال بشه و در صورت نیاز، فایل‌های مرجع دیگه هم در اختیار ایجنت قرار می‌گیره.

هیچ اسکریپتی اجرا نمی‌شه و چیزی هم در پس‌زمینه نصب نمی‌شه. همه‌چیز فقط دستورالعمل متنیه.

## نصب و راه‌اندازی

اگه از ابزارهای پشتیبانی‌کننده Skills استفاده می‌کنی، می‌تونی با دستورهای زیر اسکیل‌ها رو نصب کنی:

```bash
# نصب هر ۹ اسکیل
npx skills@latest add OWNER/hone --skill '*'

# نصب فقط یک اسکیل مشخص
npx skills@latest add OWNER/hone --skill debug-connectivity
```

یا می‌تونی پوشه‌ها رو مستقیماً کپی کنی داخل مسیری که ایجنتت اسکیل‌ها رو از اونجا می‌خونه؛ مثلاً:

- `~/.claude/skills/`
- `.agents/skills/`
- فایل‌های پرامپت اختصاصی

فقط حواست باشه بخش `frontmatter` فایل‌ها رو تغییر ندی؛ چون اطلاعات مربوط به زمان فعال شدن اسکیل‌ها همون‌جاست.

## چرا دقیقاً این ۹ تا؟

این ۹ اسکیل برای موقعیت‌هایی انتخاب شدن که AI ممکنه یه خروجی ظاهراً درست تحویلت بده، در حالی که پشت ماجرا هنوز یه مشکل جدی وجود داره.

چند نمونه:

- **اتصال رو بررسی نمی‌کنه:** فقط از روی یه Promise موفق نتیجه می‌گیره که ارتباط برقرار شده.
- **به محیط واقعی دسترسی نداره:** بدون بررسی وضعیت سیستم، می‌ره سراغ تغییر کد و حتی ممکنه مشکل رو بدتر کنه.
- **چیزی رو اندازه‌گیری نمی‌کنه:** بدون پیدا کردن گلوگاه اصلی، شروع می‌کنه به بهینه‌سازی بخش اشتباه.
- **ریسک تغییرات رو نمی‌بینه:** روی فرمت و ظاهر کد تمرکز می‌کنه ولی یه Migration خطرناک رو نادیده می‌گیره.
- **محدودیت‌های خودش رو قبول نمی‌کنه:** توی گزارش انتشار می‌نویسه یه پلتفرم تست شده، در حالی که اصلاً چنین تستی انجام نشده!

یه ویژگی مهم توی تمام این اسکیل‌ها وجود داره:

**هر اسکیل با یه تعریف مشخص از «انجام شدن کار» تموم می‌شه.**

یعنی ایجنت باید مشخص کنه دقیقاً چی رو بررسی کرده و چه چیزهایی هنوز تست نشدن.

از نظر ما، گفتن «این مورد بررسی نشده» خیلی بهتر از اینه که AI با اعتمادبه‌نفس یه موفقیت الکی اعلام کنه.

## ساختار هر اسکیل چطوریه؟

| قانون | دلیلش چیه؟ |
| --- | --- |
| فعال شدن بر اساس توضیحات و نیاز کاربر | ایجنت باید منظور کاربر رو بفهمه، نه اینکه فقط دنبال اسم یه ماژول بگرده |
| بررسی واقعیت قبل از اجرای دستورالعمل | اطلاعات ثابت، خطاها و دستورهای واقعی جلوی حدس‌های اشتباه رو می‌گیرن |
| بخش Anti-patterns | دونستن کارهایی که نباید انجام داد، گاهی از دونستن Best Practices مهم‌تره |
| دستورالعمل کوتاه + جزئیات در `references/` | قرار نیست ایجنت برای انجام یه کار ساده، ۶۰۰ خط مستندات بخونه |
| تعریف دقیق پایان کار | مشخص می‌کنه چی انجام شده و چی هنوز بررسی نشده |
| بدون کد اجرایی | اسکیل فقط دستورالعمله؛ چیزی رو نصب، اجرا یا ارسال نمی‌کنه |

برای بررسی بخش‌های فنی و ساختاری هم خود مخزن یه سری تست داره.

دستور `npm test` موارد زیر رو بررسی می‌کنه:

- درست بودن `frontmatter`
- هماهنگی اسم اسکیل با پوشه مربوطه
- طول توضیحات
- وجود فایل‌های مرجع
- ساختار تیترها
- هماهنگی فایل [`catalog.json`](catalog.json) با اسکیل‌های موجود

اگه خواستی خودت اسکیل جدید بسازی، مستندات [`docs/fa/writing-a-skill.md`](docs/fa/writing-a-skill.md) رو بخون.

## بررسی و تست

برای اجرای تست‌ها از دستورهای زیر استفاده کن:

```bash
# بررسی هر ۹ اسکیل و لینک‌های داخلی مستندات
npm test

# ساخت مجدد catalog.json بعد از اضافه کردن یا تغییر نام اسکیل
npm run catalog
```

این پروژه مرحله Build یا درخت وابستگی جداگانه‌ای نداره.

حتی پوشه `node_modules` هم عمداً داخل مخزن قرار نگرفته.

**وضعیت انتشار:** این پوشه از قبل یه مخزن Git با تاریخچه مشخص داره. قبل از انتشار، دو نکته‌ای که باید بدونی داخل فایل [`PUBLISH.md`](PUBLISH.md) نوشته شده.
